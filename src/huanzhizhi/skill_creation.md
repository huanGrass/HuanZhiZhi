# 技能开发知识索引

这里的技能是宿主加载的普通 Python 程序（`task.py`、`skill.json` 和必要资源），不是 Codex 的 `SKILL.md` 指令包。所有游戏使用同一个创建入口；窗口观察和具体规则由本次目标决定，宿主不按游戏名称分流。

## 状态与动作驱动的开发

创建和运行分为两个阶段，不要求新建框架、接口或固定数量的文件。

### 创建：探索、留样、固化

1. **理解并操作。** 先查看相关的已有实现和共享组件。通过宿主内部截图和输入接口，像看图操作一样走必要的几步，确认任务规则、状态变化和动作含义。AI 可在这一阶段看图判断；不先实现完整识别器，也不要求只走一步或固定步数。
2. **保存对应证据。** 在本次草稿保留操作前后图像、状态标注、逻辑动作、实际输入及核对结果。用字段含义和真实样例明确“图像要转换成什么状态、求解输出什么动作”。AI 标注须由实际变化和已知规则核对；未知不能当空白，预测不能当观察结果。
3. **生成可重复运行代码。** 优先复用已有实现，按缺口编写本地图像识别、求解和动作转换。用保留样本核对识别结果，再通过原宿主入口运行。资源不足时按具体缺口补采，不穷举画面或另写测试框架。成品只带代码与必需资源，不依赖开发 Agent、远程看图或草稿路径；用户明确需要运行时模型的任务除外。

### 运行：识别、求解、执行或提示

- **识别**：截图转为领域状态；界面位置、选中反馈等执行信息与领域状态分开使用。已有结构化输入的任务跳过识图。
- **求解**：输入状态、规则和必要历史，输出逻辑动作，不读取图像和屏幕坐标。复用已安装求解器；同一运行会话中复用引擎和截图资源。
- **动作转换**：把逻辑动作映射为当前界面的坐标或输入步骤。自动模式执行，提示模式只展示同一个动作，等待用户实际操作；用户可执行其他合法动作。
- **观察推进**：两种模式都以真实画面变化更新状态，复用规则核对结果。显示提示、发送点击和预测局面均不代表动作已完成。

简单函数和现有组件足够时直接使用。界面专属识别和操作留在技能包；宿主只负责开发会话、输入通道、任务生命周期与保存。修改已有技能只处理本次需求，不重写无关功能。

## 验证与交付

- 修复前先复现，以实际调用链、日志或测试确认根因；证据不足只调查。复杂度必须解决当前已证实的问题，不预建恢复策略和多路识别。
- 每次输入前检查停止、目标窗口和状态有效性；选中反馈不明确不发后续输入。等待和重试有界且可停止；暂停恢复后丢弃失效观察。保留数据保护、输入校验和必要错误处理。
- 通过现有宿主入口核对真实结果、所需模式及暂停停止。连续技能检查后续运行成本，按识别、求解、输入和外部等待定位耗时，对照已有实现或用户要求；不设任意统一秒数，不为凑次数重复运行。
- 修复后先结合代码改动与已有记录判断证据是否仍有效，只补验受影响部分及尚未覆盖的要求。仅修停止回执时保留已通过的业务结果，补验停止；仅修提示转发时补验真实提示和清除，不重跑未受影响的自动模式。识别、求解或共用动作逻辑改变时，重验依赖它们的模式；影响不明时扩大验证。记录仍有效的证据与本次补验范围即可。
- 创建过程不编写测试脚本、模拟用例、临时启动器或额外审计报告。复用保存的样本、宿主记录和固定短运行入口。未取得的证据如实说明，不能把首次成功冒充完整需求通过。
- 收尾沿用[入口示例](skill_reference.md#skilljson-与入口最小示例)中的现有 SDK 和资源关闭方法；结束回执只由一处负责。宿主负责提示展示与退出兜底，技能不为验收而枚举桌宠窗口或复制宿主内部逻辑；实际显示仍通过宿主画面及事件确认。
- 技能根目录只交付代码、清单和必需资源。运行数据统一用 `session.runtime_dir`：截图与日志放 `runs/`，可清理缓存放 `cache/`，续局等持久状态放 `state/`。修改验证使用草稿自己的运行目录，宿主保存时保留原技能状态。
- 创建的新技能由宿主保存到测试分组；修改时由宿主检查外部变更、备份和替换。开发 Agent 不直接修改宿主源码或已安装技能。停止、未完成或验证失败时保留草稿。

## 互动体验验收

用于互动方案调查、新建及涉及体验的修改；普通设计细节自行决定，不增加用户审批，用户明确要求优先。

1. **具体承诺。** 用一段完整交互说明用户输入、角色行为、对象响应、结果反馈和恢复操作；给出可观察的通过标准与失败表现。核对素材能否表达动作及其触发、时机和结束条件。角色若承担核心职责，移除后体验不应完全相同；若定位是装饰或陪伴则按该定位判断。
2. **符合场景。** 说明哪些元素常驻及原因，其余按需出现。桌面互动以角色和交互对象为主体，检查实际背景下的遮挡、可读性与视觉层次；透明窗口或通用动画本身不代表体验达标。
3. **先验证核心。** 开发时先在真实宿主打通最小完整交互，查看角色与场景合成后的实际画面。用短录屏或按事件顺序的关键帧检查动作语义、连续性、接触关系及反馈，再补齐其余功能；已有部分复用检查，不重复搭原型。
4. **对照证据。** 在现有开发记录中按“承诺—实际证据—通过或缺口”分别判断功能和体验，主动找未兑现的要求。状态变化、坐标正确或有截图不能代替体验结论，自动操作不等于人工手感认可。缺口修正后再交付；无法满足时说明具体限制和取舍，不冒充完成。
